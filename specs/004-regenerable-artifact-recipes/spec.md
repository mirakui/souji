# Feature Spec: recipes for regenerable build artifacts

**Status**: implemented
**Date**: 2026-09-18
**Affects**: `lib/souji/fs_scan.rb`, `lib/souji/terraform/root.rb`,
`lib/souji/node/project.rb`, `lib/souji/python/venv.rb`,
`lib/souji/recipes/{terraform_dir,node_modules,python_venv}.rb`,
`lib/souji/recipes/{git_worktree,terraform_provider}.rb`, `lib/souji/plan.rb`,
`lib/souji/commands/init_command.rb`, `README.md`, `.rubocop.yml`,
`spec/support/fs_fixture_factory.rb`

## Problem

A real cleanup of a 460 GB workstation down to 18 GB free found that the
overwhelming majority of the reclaimable space was regenerable build output,
and that souji could automate almost none of it. Of the runbook's steps, only
the worktree inventory had a recipe. The three largest piles did not:

| Artifact | Measured | Regenerated by |
|---|---|---|
| 85 `.terraform/` directories | 39.6 GB | `terraform init` |
| 31 `node_modules/` trees | 8.5 GB | `pnpm install` and friends |
| 33 virtualenvs | 8.9 GB | `uv sync` and friends |

These are three instances of one shape: a directory that is expensive to keep
and cheap to rebuild, *provided* the recipe for rebuilding it is still on disk.

## Goals

- Reclaim each of the three, with per-ecosystem safety knowledge owned by
  souji rather than by the scenario file.
- Never propose an artifact souji cannot prove is rebuildable.
- Never propose an artifact whose rebuild would produce something different
  from what was deleted.
- Measure staleness from the artifact, not from the project.
- Extract the filesystem primitives the three share exactly once.

## Non-goals

- **A generic `stale-dir` recipe.** Parameterising a directory name would move
  "what is safe to delete" from souji into the scenario, which is the one place
  it must not live. Dedicated recipes cost more code and buy the safety
  guarantees that are the point of the tool.
- **A `require_lockfile: false` escape hatch.** See the decisions below.
- **Android SDKs, Chrome profiles, Lightroom temp files** and the other
  one-off paths in the runbook. Each is a single path a human can inspect;
  none is a rule souji can state.
- **Emptying the trash.** souji sends things to the trash, and the space is
  not returned until the trash is emptied. That remains the user's action.
- **Writing `~/.terraformrc`.** Enabling the shared provider plugin cache
  prevents `.terraform/` from re-inflating, but it is a configuration change,
  not a deletion, and souji only deletes.

## Decisions

### D1. `terraform-dir` deletes children of `.terraform/`, never the directory

A census of the 85 real directories found: `providers` 84, `terraform.tfstate`
60, `modules` 20, `environment` 2, `archive` 1.

Two children are not regenerable. `environment` records the selected
workspace, and losing it silently reverts you to `default`, so the next
`terraform apply` targets the wrong workspace — the worst outcome a
disk-cleanup tool could cause, and two of the real directories are on `prd`.
`.terraform/terraform.tfstate` is the cached *backend configuration*; re-init
usually rebuilds it from the `backend` block, but under partial configuration
(`terraform init -backend-config=...`) it is the only on-disk record of which
bucket and key were used, and nothing in the file says which case you are in.

Choosing a deletion unit that *cannot* include them dissolves the hazard
rather than guarding against it: no skip rule is needed, and the two
production roots stay eligible for the rest of their cleanup. A **denylist**
rather than an allowlist also means the recipe keeps reclaiming whatever
terraform adds next — an allowlist of `{providers, modules}` would already
have missed `archive/`.

Cost: ~105 plan items instead of 85, and an almost-empty `.terraform/` husk
left behind. The plan YAML is explicitly a review artifact, so more rows with
clearer provenance is the right trade.

### D2. Staleness is the artifact's own generation time

The single largest real case has sources edited *today* and a 1.5 GB
`.terraform/providers` from *ten months ago*. Any rule keyed on project source
activity would have excluded precisely the biggest win.

The reasoning generalises: the regeneration recipe's presence has already been
proven (rule D3), so project activity does not make the artifact less
rebuildable — it only predicts how soon you will pay for the rebuild. So all
three recipes gate on the artifact:

| Recipe | Signal |
|---|---|
| `terraform-dir` | `.terraform/terraform.tfstate`, `providers/`, `modules/modules.json` |
| `node-modules` | the install receipt: `.modules.yaml`, `.pnpm-workspace-state.json`, `.package-lock.json`, `.yarn-integrity`, `.bin`, then the directory's own mtime |
| `python-venv` | `lib/python*/site-packages`, then `bin`/`Scripts`, then `pyvenv.cfg` |

Project activity is recorded as `project_at` so a reviewer can see both, and
never gates.

Two candidate signals were considered and rejected for `node-modules`. The
directory's own mtime is unreliable in both directions, so it is kept only as
a last-resort fallback where its error is conservative (a spurious touch makes
souji propose *less*). The **lockfile's** mtime is actively wrong: it measures
when dependencies changed, so a project installed yesterday from a year-old
lockfile would look a year stale. It is recorded as `lockfile_at` for
information only.

### D3. A lockfile or manifest is always required, with no way to relax it

`node-modules` requires a sibling lockfile; `python-venv` requires a sibling
regeneration manifest; `terraform-dir` requires a sibling
`.terraform.lock.hcl`.

The rule is about *what comes back*, not about how long the rebuild takes. An
`npm install` with no lockfile re-resolves semver ranges; a `terraform init`
with no lock file resolves fresh provider versions. In both cases the
reconstructed tree is not the tree that was deleted — a behaviour change
dressed up as a cache miss. A `require_lockfile: false` parameter would let a
scenario opt out of exactly the guarantee the recipe exists to provide, so
there is no such parameter. All 85 real terraform roots carry a lockfile, so
strictness costs nothing here.

`node-modules` additionally requires that `package.json` *parses*: a manifest
souji cannot read is a reinstall souji cannot promise.

### D4. Safety rules live in an object shared by plan and apply

`souji apply` never re-reads the scenario (FR-011a), so `#verify` has to
re-apply exactly the rules `#enumerate` applied. Rules that must agree live in
one object — `Souji::Terraform::Root`, `Souji::Node::Project`,
`Souji::Python::Venv` — following `Souji::Git::WorktreePolicy`. Each exposes a
single `#blocker`, and each recipe's `#recheck` is called from both paths.

For `terraform-dir` this is not a nicety: the most valuable re-check is "did a
`terraform apply` start in the last five minutes?", and the window between
plan and apply is exactly where that lives.

### D5. Apply-in-flight detection, and the saved-plan zip magic

A terraform root is refused while any of these exist: a held
`.terraform.tfstate.lock.info`, a leftover `errored.tfstate`, or a saved plan
file. `terraform apply <saved-plan>` demands the exact provider binaries
recorded in the plan, so clearing `.terraform/providers` invalidates a pending
apply.

A saved plan is identified by its **first four bytes being `PK\x03\x04`** (a
saved plan is a zip archive), not by its name. Real roots on the measured
machine keep a human-readable `tfplan.txt` dump beside the real `tfplan`, and
a name-only rule would let that dump block cleanup forever. A saved plan older
than the caller's own `older_than_days` does not block, because terraform
itself refuses a plan whose state serial has moved on.

### D6. Structural venv detection, and the immediate-parent rule

A venv is recognised by a PEP 405 `pyvenv.cfg` plus an interpreter, not by
directory name. A name list would match any directory someone called `venv`
while missing every venv called something else, and the structural check costs
one extra stat per visited directory.

Conda and mamba environments carry `conda-meta/` and no `pyvenv.cfg`, so they
never match — correct, since removing one needs `conda env remove` to keep
conda's own index consistent.

The manifest must be in the venv's **immediate parent**, never an ancestor. A
`services/api/.venv` whose only manifest is at the repository root is left
alone: souji must not assume a monorepo layout applies. The same rule puts
venvs that live one level below their project out of scope — direnv's
`.direnv/python-<version>/` and Pipenv's default
`~/.local/share/virtualenvs/<proj>-<hash>`. Those are the tool's to recreate.
`PIPENV_VENV_IN_PROJECT=1` brings the Pipenv case in.

`VIRTUAL_ENV` and `CONDA_PREFIX` are checked so the virtualenv souji is
running inside is never proposed.

### D7. Facts recorded but never used as gates

Some findings make a reviewer's judgement better without changing whether the
artifact is rebuildable, so they belong in `reason` and `metadata`, not in the
skip rules:

- `has_postinstall`, `has_patches` — patch-package re-applies on install and a
  native build only costs time. The reinstall is slow, not impossible.
- `broken_interpreter` — a venv whose base interpreter was upgraded away is
  *already* non-functional. That is a stronger reason to remove it, so gating
  on it would be backwards; it is also the most reassuring thing a reviewer
  can read.
- `workspace`, `backend_type` — read from files `terraform-dir` never deletes,
  so a reviewer can see at a glance that a root is production.

### D8. `Souji::FsScan`, and two bugs it fixed

The three recipes needed the same walk, the same size measurement and the same
age arithmetic, and each has an edge that is not obvious:

- The walk must be **deterministic** (`Dir.children(dir).sort`, so plan items
  come out in the same order every run — `GitWorktree` previously bolted a
  `.sort` onto an unordered `Find.find`), must **never follow a symlinked
  directory**, and must survive an unreadable subtree.
- `dir_size` must **lstat**, not stat. With `TF_PLUGIN_CACHE_DIR` in use, a
  `.terraform/providers/**/<os_arch>` entry is a symlink into the shared
  plugin cache; following it both inflated the item's size and double-counted
  it against `terraform-provider`.
- Each recipe passes a `skip:` list with **its own target removed**, which is
  also why one shared walk across recipes is impossible.

Migrating `TerraformProvider#collect_referenced` onto it fixed a real bug: it
walked with a bare `Find.find` and **no pruning at all**, descending into
every `node_modules` and `.terraform` on the machine. Besides dominating the
scan, that meant a `.terraform.lock.hcl` vendored inside a dependency tree
pinned the provider cache — a vendored fixture is not a statement about what
this workstation depends on.

`FsScan.staleness` resolves an `older_than_days:` threshold to `:stale`,
`:unknown` or `[:fresh, days]` and leaves the wording to the caller.
`:unknown` is a refusal, not a pass: a threshold the user asked for that souji
cannot evaluate has not been satisfied.

### D9. No default for `older_than_days:`

Omitting it means no age filter, matching every existing recipe: souji
proposes everything satisfying its safety rules, and narrowing is the
scenario's business. This also matches the runbook's intent for `.terraform/`,
which was to clear all 85 of them.

### D10. `terraform-dir` and `terraform-provider` are order independent

`terraform-provider` computes its referenced set from the
`.terraform.lock.hcl` files; `terraform-dir` requires one and never deletes
one. So clearing `.terraform/providers` cannot orphan a cache entry, in either
order, within a run or across runs. Documented in the README so nobody
re-derives a non-existent ordering rule.

The interaction that *is* real: `git-worktree` items and these three **nest**,
since a worktree can hold a `.terraform/`. Apply processes items in scenario
declaration order, so declaring `git-worktree` first means the worktree goes
to the trash as one unit and each nested item's `#verify` reports `already
removed`. The plan's byte total double-counts in that case — a documented
cosmetic limitation, not a correctness bug.

### D11. `Metrics/ParameterLists: CountKeywordArgs: false`

Keyword arguments do not carry the readability cost this cop exists to catch:
they are named at every call site and order-independent. Every place souji had
hit the cop — `Plan#initialize`, `PlanItem.new`, `ActionLog#record` — is a
keyword-only constructor with an inline disable. Three disables for the same
reason is a configuration decision wearing a disguise, so the disables are
gone and the cop is configured.

## Test plan

- `spec/unit/fs_scan_spec.rb` — deterministic order, `:prune`, `skip:`,
  symlinked directories and symlink loops, unreadable subtrees, lstat-based
  sizing, the `newest_mtime_under` budget, `days_since`, `staleness`.
- `spec/integration/recipes/terraform_dir_spec.rb` — child-entry items,
  preserved entries, missing lockfile, missing configuration, all three
  apply-in-flight blockers, `tfplan.txt` *not* blocking, a stale saved plan
  not blocking, symlinked `.terraform`, walk pruning, artifact-vs-project
  staleness, and the `#verify` re-checks (in-flight apply, re-init,
  hand-edited plan naming a preserved entry).
- `spec/integration/recipes/node_modules_spec.rb` — the real workspace-root
  shape (lockfile, no manifest), unparseable manifest, missing lockfile, each
  package manager, nested trees, monorepo composition, receipt precedence,
  install-vs-lockfile and install-vs-source staleness, `#verify` catching a
  reinstall.
- `spec/integration/recipes/python_venv_spec.rb` — structural detection, a
  directory merely named `venv`, conda, manifest precedence, the
  immediate-parent rule, the active virtualenv, `broken_interpreter` not
  gating, `#verify` catching an install.
- `spec/integration/recipes/terraform_provider_spec.rb` — a vendored lockfile
  no longer pins the cache (the D8 behaviour change).
- `spec/support/fs_fixture_factory.rb` builds real directory layouts rather
  than stubbing the filesystem: each recipe is a set of claims about what a
  layout *means*, and a stub can only confirm the claim we already believed.
- `spec/unit/recipe_registry_spec.rb` and
  `spec/integration/recipe_contract_spec.rb` cover the new recipes through
  `BUILTIN_NAMES`; `spec/integration/cli_init_spec.rb` already enforces that
  the init template documents every declared param and stays ASCII-only.
